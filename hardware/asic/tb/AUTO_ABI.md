# Autonomous proof verification

The top-level default `AUTO_VERIFY=1` enables the fixed verifier in the synchronous ROM. The build emits both its initialized SystemVerilog and an equivalent little-endian word image for the Rust interpreter. The ROM holds RV64I control instructions, field and Keccak instructions, constants, and protocol labels. The verifier reads the serialized proof and a trusted public statement descriptor. The Rust descriptor generators take public inputs. The proof, parser offsets, challenges, indices, siblings, and expected intermediate results are absent from their inputs.

## Command port

Preload the descriptor and proof on word boundaries. Either may come first. The byte count excludes padding in the last SRAM word. Leave space above both inputs for the verifier stack. Scratch allocations, including the two Steiner frontiers, kernel points, coefficient tables, and gate registers, use the existing SRAM. The controller checks its scratch boundary on stores. The scalar registers use Poseidon context slots 1 through 3. Slot zero holds the Poseidon2-12 state during message hashing and the two operands during Fp5 instructions.

| Command | Fields | Completion |
| --- | --- | --- |
| `0x08` | `idx=1` | Clears both sticky status fields (`pass=1, checks=0`; callers MUST also require `checks > 0` to accept a proof) |
| `0x50` | `addr=descriptor_word`, `data={total_bytes[31:0], window_words[15:0], proof_word[15:0]}` | Returns 1 for acceptance (`checks > 0`), 0 for failure, or a page request; sets sticky `verify_fail` if `AUTO_VERIFY=0` |
| `0x51` | `data=zero_extended_requested_byte_offset` | Resumes after refilling the requested page |
| `0x0b` | Existing status command | Bit 32 is the sticky success flag (`~verify_fail`). Bits 31 through 0 count completed hardware checks (host drivers MUST require `pass && checks > 0`) |

Set `window_words=0` for the three-command path. For paged input, reserve at least two consecutive SRAM words and preload the first window. Descriptor and scratch storage stay resident. A page request has response bits 63 through 56 equal to `0x51` and bits 31 through 0 equal to the next aligned proof **byte** offset. Refill up to `window_words * 8` bytes starting there into the original SRAM window. The last word can be padded. An unaligned eight-byte load at the boundary can request one word of overlap. The page bench checks that requested offsets strictly increase. During a pause the host can use `0x03` on the window, or load `[proof_word .. proof_word + window_words)` by PCIS DMA on AWS F2, then echo the offset with `0x51`. Out-of-window writes (both `0x03` and AWS F2 PCIS DMA) and mismatched continuations are rejected / terminate the invocation with failure.

## Descriptor encoding

All integers are little-endian. A blob starts with its 32-bit byte length. The first four bytes of either descriptor give its total byte length including that header. The next four bytes select the protocol. Treat the descriptor as the caller's public verification key and statement. Generate it independently of the proof provider.

* `ZKD1` selects non-lookup `QSAGZKH2`, wire tag 17. The remaining fields are the 32-byte shape digest, layout blob, statement blob, public-input blob, 32-bit S-box row count, and row-compressed matrices A, B, C. Each matrix has one row for every padded row in the shape. Each row stores a 32-bit entry count followed by pairs of 32-bit column index and 64-bit canonical coefficient. The layout blob uses the Rust transcript serialization. The hardware derives the canonical WHIR geometry and compares the supplied schedule to it.
* `HQD1` selects `QSAGHQM2`, wire tag 1. The fields are the bitmap blob, serialized committee blob, one-byte signing mode, mode payload blob, 32-bit log rows per signer and 32-bit active signer count. The committee has one 65-byte key per bitmap position. In ascending active-index order, the ROM checks each profile, checks all eight little-endian limbs against the Goldilocks modulus, and rejects repeated active keys or mixed active profiles. The staged Rust profile IDs are 1, 2 and decimal 7 through 20. Mode 0 carries a shared message. Mode 1 carries a canonical unsigned LEB128 message count followed by length-prefixed messages in active-index order. The reader must consume the whole payload. For each signer the ROM hashes the domain, serialized key and message with Poseidon2-12, then converts the digest into the five little-endian row inputs.
* The HQM2 public row program immediately follows the active signer count. Its header gives the number of distinct operations and the size of the step-constant pool. The 64-bit constants are followed by one pair of 16-bit indices per local step for its selector and constant. The gate program then gives the register count, result register, constant count, 64-bit constants, instruction count and 32-bit instructions. Each instruction packs a two-bit opcode and three ten-bit register indices in destination, left, right order. Opcodes 0, 1 and 2 add, subtract and multiply Fp5. Opcode 3 loads a base constant using the low 20 bits as its index.

The ZK descriptor emitter is `tb/rust/auto/fixture.rs::descriptor`. The HQM2 emitter is `tb/rust/auto/statement.rs::hqm`. It records the Rust generic row evaluator over symbolic inputs, shares common subexpressions, and assigns SRAM slots by last use. The ROM computes row and column challenges, selectors, and the gate inputs at verification time. The verifier still relies on the caller to supply the authentic profile-specific row program and step constants. A deployment accepting descriptors from an untrusted host must authenticate these verification-key fields.

## Verification

Run `bash tb/verify_auto.sh` on the dedicated build host. The generated SystemVerilog embeds the ROM contents and can be elaborated from any working directory. The Rust instruction oracle reads the matching hex file. Regeneration uses the staged clang cross-compiler and selects 2,048 or 4,096 words according to the firmware byte length. The regression runner uses hierarchical Verilation of the original arithmetic RTL. The arithmetic leaves execute their generated gate logic.

The Rust mutation manifests name each proof field, byte offset and bit. On Linux the bench forks a simulation at the first bus read of the word containing each mutation. The child flips the SRAM bit before the read edge, runs the remaining RTL clocks and reads sticky status. The parent checks each exit status, the number of unique mutations actually launched and positive-proof acceptance. The non-canonical replacement and length cases run separately.

The formal miters cover the ordered-insertion iteration, the Steiner sibling/parent decision and the shifted-coset butterfly schedule composed with Goldilocks/Fp5 operations. The insertion proof uses a prefix invariant and an arbitrary membership witness. The butterfly proof interprets the control words elaborated from the RTL. The split between those local contracts and the complete verifier is exercised by the command-port tests.
