# QSAG quorum custody and consensus scaling

This report sizes QSAG for validator sets from 1,500 to 1,048,576, for sparse signer sets drawn from directories of up to 2^37 principals, and for a hardware verifier. Every table is generated by [`scripts/quorum_and_consensus_scaling.py`](../scripts/quorum_and_consensus_scaling.py), which runs no prover. Each number carries one of three tags:

- **measured**: one recorded release run on named hardware;
- **exact**: arithmetic on a wire format or a relation's geometry;
- **model**: a projection whose inputs and formula are stated in the script and in "Model definitions" below.

## Summary

Hem aggregates signatures from independently controlled validator keys. Threshold custody distributes control of one key. The two compose (a custody committee produces one validator signature, with no extra bytes in the aggregate) but neither replaces the other.

**One shard (measured).** 128 `JortsPoseidon2` signers occupy a 24-variable trace. The proof is 445,566 bytes, takes 3.67 s on an Intel Core i9-12900 and 1.56 s on an AMD Radeon RX 6750 XT, and verifies in 3.00 ms (6.21 ms on one core). At 256 and 512 signers (25 and 26 variables) the proof is 480,342 and 556,830 bytes. The GPU prover commits 25- and 26-variable witnesses entirely in 12 GiB of VRAM (round-0 commit 1.65 s and 3.44 s).

**Subtree recursion.** A shard can be proved in a recursion-friendly form whose verifier is itself a Hem relation. `SubtreeLeafMergeRelation` verifies up to 16 such shards; `SubtreeInternalMergeRelation` verifies up to 16 merges. Both expose the same 14-word public statement, so merges nest to any depth and the root is one `SuccinctSubtreeAggregate` whose size depends only on the arity of the last merge: 312 to 340 KiB (model, exact in every term but the WHIR openings). It verifies in 11.5 ms on one core (measured) against a 32-byte roster root and a verifier key under 256 bytes. No child proof, public-key list or bitmap reaches the verifier.

**Two schedules (model).** Two quaternary levels cost less prover time than one 16-ary level and give a smaller root, so the latency-optimal tree is narrow and deep; each level is a network hop, so the hop-optimal tree is wide and shallow.

| Schedule | Shards | 100,000 validators | 1,048,576 validators |
| --- | --- | --- | --- |
| LAN: 128-signer shards, arity 4 | one GPU each | 3.52 s, 5 levels | 4.28 s, 7 levels |
| WAN: 512-signer shards, arity at most 16 | one GPU each | 8.85 s, 2 levels | 9.53 s, 3 levels |

These are critical-path proving times with one prover per tree node and every stage on a GPU. They exclude network transfer between levels.

**Dual path.** A live vote is one `Compact1122` signature in one datagram; the transferable certificate is the root proof above, over a second, Poseidon2-based signature from each validator. The first carries the slot; the second is what a bridge, light client or archive checks.

**Beyond validator sets (model and design).** The same 14-word statement supports sparse signer sets from a directory of 2^37 keys without a bitmap, which is the basis of the three-tier "hyperweb" sizing below. The verifier uses five word-local primitives and no big-integer arithmetic, so it fits a logic budget of 954 kGE; the silicon tables are a budget, not a tape-out.

The model uses only the Python standard library. `--self-test` checks the arithmetic, the schedules, every figure quoted in this prose, that each modelled leaf time lies between its measured anchors, a set of source-drift guards (public-statement width, wire magic, merge arities, GPU variable limit, packet constants), and byte equality of the generated block below. It is not a Rust test and proves nothing about soundness.

Bytes are decimal unless a binary unit is written. Bandwidth figures count one delivered copy.

## Model definitions

**Leaf.** A recursive shard of K signers commits two witnesses: the 256-column trace and the fixed-path auxiliary witness that makes its openings cheap to verify in a circuit. Measured anchors: the CPU child prover (4.44, 8.73 and 17.02 s at K = 128, 256, 512 on a Ryzen 9 9950X), the GPU single-WHIR shard at K = 128 (1.33 to 1.56 s), the GPU round-0 commit at K = 256 and 512, and the GPU Poseidon2 Canopy tree (2^20 leaves in 79 to 83 ms). The modelled GPU recursive-shard time (1.62, 3.15, 6.35 s) scales the K = 128 shard by the measured commit ratio and adds the Canopy build. It has not been measured end to end.

**Merge node.** A merge of arity b verifies b children inside a public one-table Hem relation with a committed (holographic) description of its own constraint matrices; that commitment is what lets a merge be a child of another merge. Its padded size doubles with b: 2^17 rows at b = 2 to 2^20 at b = 16. Prove times (0.22 to 1.25 s GPU, 0.85 to 6.40 s CPU) are linear in padded rows from the quaternary point and are a model.

**Root proof.** Row, column and matrix sumchecks and the lookup argument are exact counts of quartic-extension elements for the padded geometry; the three WHIR openings are a linear fit (282,000 B at 19 lookup variables, 6,400 B per additional variable); the header is 40 bytes.

**Critical path.** One leaf prove plus one merge per level. **Cluster work** is the sum over all nodes.

**Roster.** The roster is a Poseidon2 Merkle tree over key records ordered by key index. A dense leaf merge hashes its shard's keys into a subtree root; a sparse leaf merge opens each signer's path to the directory root inside the relation. Every merge exposes the minimum and maximum key index beneath it and requires its children's intervals to be strictly increasing, so no signer is counted twice at any depth and no bitmap is needed. Building the tree is linear in the roster and happens once per epoch; verifying an aggregate never touches it.

**Silicon.** Gate counts are taken from published cores for the same primitives and from the multiplier count of a four-lane extension-field datapath; densities, clocks and power are typical figures for each node. Cycle counts are estimates for that datapath.

## Reading the tables

**Arity.** Root size grows by under 10 KiB per doubling of arity, while merge time doubles. Two quaternary levels (0.76 s) therefore beat one 16-ary level (1.25 s) and produce a root 19 KiB smaller. Arity is a deployment choice between prover latency and the number of network hops, and the relation accepts 2, 4, 8 and 16.

**Compression.** At 1,048,576 validators the raw signatures are 4.8 GiB and the 8,192 direct shard proofs are 3.65 GB; the root proof is about 330 KiB, four orders of magnitude below the shard proofs. Direct verification remains available and needs no recursion; it costs 6.21 core-ms and 445,566 bytes per shard.

**Beam.** 2,048 validators in eight 256-signer shards and one 8-ary merge have a modelled critical path of 3.83 s, inside a four-second slot only with GPUs at every node and no allowance for transfer. 8,192 and 16,384 validators (4.21 s and 4.51 s) pipeline across slots. On CPUs the measured child prover alone exceeds the slot.

**Live path.** A BLS aggregate with a signer bitmap stops fitting one 1,232-byte datagram above 9,088 validators. A `Compact1122` vote with its 96-byte header is 1,218 bytes at any validator count, so a sampled quorum of single-datagram votes scales where a bitmap certificate does not. Verification is the cost: 1.03 ms per vote on one core (measured), so 1,200 votes inside 150 ms need about nine cores. `Compact1122` is a Keccak scheme and is not what Hem aggregates; the finality certificate is over each validator's `JortsPoseidon2` signature. A height-20 key signs 2^20 times in the same 512-row trace slot as a height-6 key.

**Sparse sets.** A 128-signer leaf merge that opens every signer's path in a depth-37 directory adds 4,736 Poseidon2 permutations (558,848 S-box rows), so it pads to 2^20 rows and costs about what a 16-ary merge costs. A bitmap over the same directory would be 16 GiB.

**Hyperweb.** 8 x 10^9 people and 8 x 10^10 software agents are 2^36.36 principals; depth 37 covers them and depth 40 leaves a factor of 12. The sizing separates three objects: a session credential (161 B to 1,218 B), a streaming fold of a running claim whose opening is deferred (3,104 B per step, specified, not built), and a checkpoint (one root proof). Revocation is non-membership between two adjacent leaves of a sorted tree: 2 x 37 permutations at depth 37. Revocation trees are scoped to an issuer, because a single global deny-list would require agreement among all of its verifiers.

**Silicon.** The verifier needs Goldilocks and its quartic extension, width-12 Poseidon2, Keccak-f[1600] and carry-less multiplication, all on 64-bit words. The modelled block is 954 kGE: 0.08 to 0.19 mm^2 at 3 to 5 nm and 0.89 to 1.52 mm^2 at 28 nm, verifying one root proof in 6.8 to 17 microseconds for 0.49 to 1.45 microjoules.

## Custody is orthogonal to aggregation

| Deployment | What the signer controls | What the verifier sees |
| --- | --- | --- |
| Independent validators | One key per validator | A Hem proof over independent keys |
| Threshold validator custody | One validator key shared among custodians | One signature under that key; the committee adds no bytes |
| Threshold FIPS 205 custody | Shares of a standard SLH-DSA key | A standard SLH-DSA signature |
| Threshold custody feeding Hem | Shares that produce a `JortsPoseidon2` signature (`hem_quorum.rs`) | A Hem proof over validator keys |

A custody committee is described by a monotone access structure, not only by a threshold. Symmetric (t, n), weighted, tree-composed and per-participant (asymmetric) quorum systems compile to a monotone span program with 0/1 entries; each custodian collapses its rows into one additive share, after which signing is unchanged. Stateful signing is safe whenever any two quorums that could certify the same leaf share a custodian outside every admissible fault set; `2q > n + f` is the symmetric case.

## What is measured, and what is not

Measured: the single-WHIR shard at 24 to 26 variables on CPU and at 24 variables on GPU; the recursive-shard child prover on CPU; the GPU round-0 commit at 25 and 26 variables and the GPU Canopy tree; hologram root verification; `Compact1122` batch verification.

Modelled: the GPU recursive-shard prove, every merge-node time, root proof bytes (through the opening term), cluster work, the streaming edge fold, and all silicon figures. No tree deeper than two levels has been timed end to end, no tail latencies are reported, and no table includes network transfer between tree levels.

Not addressed by arithmetic: stake-weight policy, slashing, key rotation cadence, and the consensus protocol itself.
